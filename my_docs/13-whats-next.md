# 第十三章：架构对比与下一步（复盘章，无代码）

## 复盘四块

### 1. 全景主线：文件按离循环的远近分四层

```
【前置层】循环跑起来之前   cli.ts 喂输入 → prompt.ts 构造身份和工具表
【运行时】循环的每一步     tools.ts 动手 → permissions 闸门 → context.ts 看预算
【持久层】循环结束之后     session.ts 存档本轮 → memory.ts 提炼跨轮
【扩展层】循环之外挂东西   skills.ts 加提示词 / subagent.ts 加临时工人 / mcp.ts 加外部工具
```

- 扩展层三件套的共同点：**都是往工具表或 system prompt 塞新东西，循环本体一行不改**
  （ch11/12 亲手验证：subagent/mcp 在 agent.ts 里只是拦截+路由）。扩展点收敛 = 好架构。
- context.ts 的真正角色：**减肥，不是关联**。模型记得历史不需要专门模块——messages
  数组每次整体重发，"历史关联"是 ch1 就白送的。数组快撑爆窗口时它才出手：
  budget → snip → microcompact → 摘要。防护性质：平时静默，满了才干活。
- session vs memory：**session 是录音，memory 是笔记**。session 存原样对话（忠实、
  量大、给人 resume）；memory 存从对话提炼的事实（有损、小、跨会话注入 prompt）。
  记忆的判定标准：跨会话存活 + 被提炼过。存聊天记录的活 session 已干，memory 再存即重复。

### 2. 差异三分法：简化的判断标准

| 类别 | 例子 | 性质 |
|------|------|------|
| 砍功能 | 66→12 工具、技能 2 源、去 Swarm | 多数安全，**例外：砍 abort 预算**（跑飞时无干净中断） |
| 降级实现 | 权限正则替 AST、编辑 14 步→2 步 | 有代价，代价在边缘情况，教学可忍 |
| 架构对齐 | 并行执行、缓存断点、4 层压缩、JSON-RPC | 零代价——照生产架构做的，只是规模小 |

**判断标准：代价是否只发生在边缘情况。** 在边缘（复杂危险命令、超大编辑）→ 可忍；
在主干（砍 tool_use 检查、砍权限闸门本身）→ 原理变了，不能砍。
正则抓不住 `cat file | sh`：管道每段无害，合起来是壳执行——要 AST 才看得见结构。

### 3. Hooks：四件没实现里最值得先做的

- 机制层理由：其他三件是**作者加功能**；Hooks 是**把控制权交出去**——用户不改源码，
  用配置在工具前后插逻辑。拦截策略从 switch 硬编码变成配置项 → "从工具变成平台"。
- 最小实现：matcher 命中 → spawn 子进程，stdin 传 JSON，stdout 收
  `{"action": "allow|deny"}`，deny 结果当 tool_result 回灌。协议 ~50 行。
- 真正的 ~300 行花在：**超时**（hook 卡死不拖死主循环）、**crash 隔离**（hook 挂了
  默认放行还是拦截 → 又是 fail-closed）。骨架与 ch12 MCP 子进程同构。
- 其余三件的疼点时机：AST = 被管道命令坑过才疼；LSP = 项目大到编译等不起；
  Swarm = 单上下文装不下任务（subagent 已解决"隔离"，Swarm 解决"并行探索"）。
  Hooks 是现在就疼，其余都是规模涨上去才疼。

### 4. 行数账：823 vs 5500 vs 50 万

```
agent.ts   106 行（13%）  ← 循环本体
tools.ts   335 行（40%）  ← 12 个工具
全体       823 行
```

- **循环逻辑是通用的一份，工具逻辑是专用的 N 份**：agent.ts 没有一行知道
  read_file 是什么，"调 API→查 tool_use→执行→回灌"对任何工具成立；12 个工具
  = 12 份互不相干的实现。通用一份 vs 专用乘 N，即 13% vs 40%。
- 推论：**哪里代码涨得最快，哪里最先需要架构**。工具是体积大头 → 66 工具时
  switch/case 先爆 → 教材第二阶段的 Tool 类型系统（~200 行）由此而来。
- 823→5500：功能量（ui.ts 渲染层、更多工具、双后端完整度）。
  5500→50 万：几乎全是边缘情况——兼容性、网络不可靠、输入多样性、企业级审计。
